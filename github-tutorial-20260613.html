01 — 基礎概念

Git 與 GitHub 是什麼？ 先分清楚工具和平台.

Git 是一套「分散式版本控制系統」，2005 年由 Linux 創始人 Linus Torvalds 開發。它安裝在你的電腦上，負責記錄程式碼每一次的修改歷史，讓你能隨時回到過去任何一個版本。

GitHub 則是建立在 Git 之上的雲端託管平台。它讓你把本地的 Git 儲存庫推送到雲端，並加上一整套協作工具：Pull Request、Issues、Code Review、Actions（自動化）、Pages（免費架站）等。

簡單來說：Git 是工具，GitHub 是用這個工具來協作的社群平台。類似平台還有 GitLab、Bitbucket，核心 Git 操作完全相同，差別主要在協作介面與附加功能。

Git 管理的三個區域

工作目錄 Working Directory

你在編輯器裡實際看到、修改的檔案，Git 視為「已修改 (modified)」或「未追蹤 (untracked)」。

暫存區 Staging Area

執行 git add 後檔案進入這裡，代表「準備好要被記錄成下一個版本」。

本地儲存庫 Repository

執行 git commit 後，變更被永久記錄成一個版本快照，存在 .git 資料夾裡。

為什麼需要版本控制

2005
Git 誕生年（Linus Torvalds）
2008
GitHub 上線年
100M+
GitHub 開發者數
免費
Repo 與 Pages 皆可免費使用
重點觀念
沒有版本控制時，多人協作常靠「複製整個資料夾改名 v1 / v2 / final / final2」。版本控制讓每個人都能在獨立分支上工作、互不干擾，且任何錯誤都能追溯回去、隨時復原。
Section 1 · 本節重點
  • Git = 本地版本控制工具；GitHub = 雲端協作平台，兩者不是同一個東西
  • Git 的三個區域：工作目錄 → 暫存區 → 本地儲存庫，分別對應 git add 與 git commit 兩個動作
  • 多人協作的本質是「每個人在自己的分支上工作，再透過 GitHub 整合」
02 — 核心概念

核心概念與術語. 看懂這些字，文件就讀得懂了.

開始操作前，先建立正確的詞彙地圖。下表整理 Git/GitHub 最常見、也最容易混淆的術語。

術語英文說明
儲存庫Repository / Repo一個專案的完整版本歷史與檔案集合，可以是本地或遠端
提交Commit一次變更的「快照」，附帶訊息說明改了什麼，每個 commit 有唯一 hash ID
分支Branch一條獨立的開發線，預設分支通常叫 main
HEADHEAD目前所在分支 / commit 的指標，代表「你現在站在哪裡」
遠端Remote / origin遠端儲存庫的別名，預設叫 origin，通常指向 GitHub 上的 repo
複製Clone把遠端儲存庫完整複製一份到本機，包含所有歷史
合併Merge把另一條分支的變更整合進目前分支
忽略清單.gitignore列出不該被 Git 追蹤的檔案/資料夾（如 node_modules、.env）

分支（Branch）是 Git 的核心精神

每個分支都是獨立的開發線。在 main 之外開一個 feature 分支進行開發，完成後再合併回 main，這樣主分支永遠保持「可運作」的狀態，不會被未完成的功能搞壞。

main 分支

永遠是穩定、可部署的版本，團隊共同的「事實版本」。一般情況下不會有人直接在這裡開發。

feature 分支

從 main 切出來的暫時分支，完成後透過 Pull Request 合併回 main，再刪除。

命名慣例
分支名稱沒有強制規則，但團隊常見慣例如 feature/xxx、fix/xxx、release/x.x，方便一眼辨識用途。
Section 2 · 本節重點
  • Repo / Commit / Branch / Remote / Merge 是最基本的五個詞，先搞懂這些其他文件就八九不離十
  • main 分支代表穩定版本，所有開發都在獨立的 feature 分支上進行，完成後合併回 main
  • origin 是「遠端」的預設別名，通常就是 GitHub 上的那份 repo
03 — 操作流程

基本工作流程. 從複製專案到推送變更.

下圖是 Git 四個主要區域之間的資料流動，搭配對應的指令。理解這張圖，後面所有操作都只是在這幾個步驟之間移動。

日常開發六步驟

1
Clone / Pull
取得最新程式碼：git clone 或 git pull
2
開分支
為新功能建立獨立分支：git checkout -b feature/xxx
3
修改檔案
在工作目錄編輯程式碼
4
Add & Commit
git add . 後 git commit -m "..."
5
Push
推送分支到 GitHub：git push origin feature/xxx
6
開 PR
在 GitHub 上建立 Pull Request，等待 review 與合併

常用指令速查表

指令說明範例
git clone複製遠端 repo 到本機git clone https://github.com/user/repo.git
git status查看目前哪些檔案被修改 / 暫存git status
git add把檔案加入暫存區git add .（全部加入）
git commit -m把暫存區內容記錄成一個版本git commit -m "fix: 修正登入錯誤"
git push推送本地 commit 到遠端git push origin main
git pull拉取遠端最新版本並合併git pull origin main
git branch列出 / 建立分支git branch feature/login
git checkout -b建立並切換到新分支git checkout -b feature/login
git merge把指定分支合併進目前分支git merge feature/login
git log查看 commit 歷史git log --oneline
git diff查看尚未提交的差異git diff
Commit Message 慣例
好的 commit message 讓歷史紀錄變成「專案的日記」。常見慣例是 Conventional Commits：feat: 新功能、fix: 修錯誤、docs: 文件、refactor: 重構、chore: 雜項。例如 fix: 修正登入後跳轉錯誤頁面。
Section 3 · 本節重點
  • 標準流程：clone/pull → 開分支 → 修改 → add/commit → push → 開 PR
  • git add 是「選要記錄什麼」，git commit 是「正式記錄一個版本」，兩者缺一不可
  • 養成寫 commit message 的習慣（如 feat/fix/docs 前綴），未來回溯歷史會輕鬆很多
04 — 團隊協作

GitHub 協作功能. Pull Request 是團隊合作的核心.

GitHub 真正的價值不在於「備份程式碼」，而是這一整套讓多人協作不互相干擾的流程。

Fork vs Branch

Branch（分支）

在同一個 repo 裡開一條新的開發線，需要該 repo 的寫入權限，團隊內部協作常用。

Fork（複刻）

把別人的 repo 完整複製一份到你自己的帳號下，可自由修改，完成後再用 PR 提交回原 repo，常用於開源貢獻。

Pull Request (PR) 流程

1
推送分支
在 feature 分支完成開發後 push 到 GitHub
2
開啟 PR
選擇來源分支與目標分支，寫清楚改了什麼、為什麼改
3
Code Review
團隊成員留言、建議修改，可直接在程式碼行上註解
4
CI 檢查
GitHub Actions 自動跑測試 / lint，確保品質
5
Merge
確認沒問題後合併進目標分支，分支可刪除

Issues、Projects 與 Discussions

Issues

用來追蹤 bug、功能需求、任務，可指派負責人、加標籤、連結到對應的 PR。

Projects

以看板（Kanban）形式管理 Issue 與 PR 的進度，適合追蹤整體專案狀態。

Discussions

適合放討論、Q&A、公告，不一定要變成正式任務的內容。

重點觀念
在 repo 設定中可以對 main 分支設定「分支保護（Branch Protection）」規則：禁止直接 push、要求至少一人 review 通過、要求 CI 測試通過才能合併。這是團隊協作的安全網，避免有人不小心把壞掉的程式碼直接推上 main。
Section 4 · 本節重點
  • Branch 用於團隊內部協作；Fork 用於對你沒有寫入權限的 repo（如開源專案）貢獻程式碼
  • Pull Request 不只是「合併程式碼」，更是 Code Review 與討論發生的地方
  • 設定 main 分支保護規則、強制走 PR review，是團隊協作的基本安全措施
05 — 進階功能

GitHub Pages 與自動化. 把 repo 變成網站、把流程變成自動化.

GitHub 除了存放程式碼，還能直接把 repo 內容變成一個公開網站，或是在特定事件發生時自動執行腳本。

GitHub Pages 是什麼

GitHub Pages 是 GitHub 提供的免費靜態網站服務。只要 repo 裡有 HTML 檔案，啟用 Pages 後就能透過 https://<帳號>.github.io/<repo>/ 這樣的網址直接存取，常用於專案文件、Demo 頁面、個人作品集。

啟用方式

Repo → Settings → Pages → 選擇要發布的分支與資料夾（如 main 分支的 / 或 /docs）。

更新方式

推送新的 commit 到對應分支，Pages 會在數十秒內自動重新部署，無需手動操作。

自訂網域

可在 Pages 設定中綁定自己的網域名稱，需在網域服務商設定對應的 DNS 紀錄。

實際案例
這份教學頁面本身、以及你日常的 HTML 報告，都是透過 GitHub API 推送到 jack72624-lab/claude-reports 這個 repo，再由 GitHub Pages 自動發布成可分享的網址。

GitHub Actions（自動化）

GitHub Actions 讓你在 repo 裡定義「workflow」（通常是 .github/workflows/ 下的 YAML 檔），在特定事件（如 push、開 PR）發生時自動執行，例如跑測試、building、部署。

CI 持續整合

每次 push 自動跑測試與 lint，盡早抓到錯誤，再合併進主分支。

CD 持續部署

測試通過後自動部署到伺服器或 GitHub Pages，省去手動發布步驟。

排程任務

用 cron 語法定時執行，例如每天自動整理報告或同步資料。

Section 5 · 本節重點
  • GitHub Pages：repo 裡放 HTML，開啟 Pages 設定就能變成公開網址，免費且自動更新
  • GitHub Actions：用 YAML 定義自動化流程，最常見用途是 CI（自動測試）與 CD（自動部署）
  • 你目前的 claude-reports repo 就是 GitHub Pages 的實際應用範例
06 — 常見問題

常見問題與安全須知. 新手最常踩到的坑.

問題原因處理方式
Merge Conflict（衝突）兩個分支修改了同一個檔案的同一處開啟衝突檔案，手動選擇要保留的內容，刪除衝突標記後重新 add/commit
不小心 commit 到錯誤分支在 main 上直接修改並 commitgit reset --soft HEAD~1 取消最後一次 commit（保留修改），切到正確分支重新 commit
想撤銷某次 commit發現某次變更有問題git revert <commit>，建立新 commit 來抵銷該次變更，保留歷史記錄
誤刪檔案 / 分支操作失誤git reflog 可找回近期的 commit / 分支指標，再用 git checkout 還原
.env 等敏感檔案被 commit沒設定 .gitignore加入 .gitignore 並用 git rm --cached 移除追蹤；金鑰已外流需立即更換
安全須知
絕對不要把 API Key、密碼、Token 直接寫進程式碼後 commit，即使之後刪除，舊版本的歷史紀錄裡仍然存在。正確做法是用環境變數（.env）並把它加進 .gitignore。
Force Push 風險
git push --force 會覆蓋遠端的歷史紀錄。如果別人已經基於舊版本開發，會造成混亂甚至遺失他們的 commit。共用分支（如 main）絕對不要 force push。
Section 6 · 本節重點
  • Merge Conflict 是正常現象，不是錯誤——手動解決後重新 commit 即可
  • git revert（安全，新增一筆抵銷紀錄）vs git reset（會改寫歷史，謹慎使用）
  • 敏感資訊永遠不要進 Git 歷史；共用分支永遠不要 force push
